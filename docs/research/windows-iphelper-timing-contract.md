# Windows IP Helper timing and cancellation contract

**Current development decision, 2026-10-14:** the user approved treating the missing native timing bounds and genuine stalled-route evidence as explicit development uncertainties. The revised development gate [passed local final review](ipv4-development-gate-final-review.md). This does not change any Microsoft API guarantee documented below or pass the release gate. Earlier open-gate wording records the previous decision.

Reviewed 2026-10-14 for HopVista's IPv4 milestone 1. Sources below are Microsoft API documentation; [local harness observations](go-windows-timeout-investigation.md) are identified separately. This note records the documented contract, not a feasibility-gate pass.

| Operation | What Microsoft documents | What the documentation does **not** establish |
| --- | --- | --- |
| `GetBestRoute2` | Returns the local best-route entry and best source address, or an error code. Its signature takes destination/source/interface inputs and output buffers. [GetBestRoute2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2) | No timeout, cancellation token, event, callback, or maximum wall-clock duration is specified. Therefore its documented contract cannot supply a bounded route phase or guarantee that a cutoff can interrupt a lookup already in progress. This is an inference from the published signature and remarks, not proof that the call hangs in practice. |
| Synchronous `IcmpSendEcho2` | With no event or APC routine, it waits for replies using the `Timeout` value (milliseconds), then returns a reply count; on zero replies, `GetLastError` provides extended status. The reply buffer contains response data upon return. [IcmpSendEcho2](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2) | The page does not quantify timer precision, scheduler delay, maximum overrun beyond `Timeout`, or a hard latest-return time across Windows builds and network conditions. Treating `Timeout` as a strict wall-clock deadline would add a guarantee absent from the page. |
| Asynchronous `IcmpSendEcho2` | Supplying an event or APC routine makes submission asynchronous; `ERROR_IO_PENDING` means the request is in progress. Completion is reported by event/callback, and the application parses the reply buffer with `IcmpParseReplies`. [IcmpSendEcho2](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2), [IcmpParseReplies](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpparsereplies) | Immediate submission does not establish a bounded completion time. The page does not provide an ICMP-specific method to cancel a pending request or authorize freeing its response storage merely because an application deadline passed. |
| `IcmpCloseHandle` | Closes a handle opened by `IcmpCreateFile` or `Icmp6CreateFile`; returns whether the handle closed successfully. [IcmpCloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpclosehandle) | Its page does not say that closing the handle cancels a pending ICMP request, waits for completion, or makes pending buffers safe to reuse. Do not treat successful close as an established cancellation or drain contract. |
| General Windows I/O cancellation | `CancelIoEx` marks operations on a **file handle** for cancellation and does not wait for completion; `CancelSynchronousIo` marks operations issued by a specified thread and likewise does not wait. Microsoft warns that drivers may not support cancellation and some operations cannot be canceled. [CancelIoEx](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex), [CancelSynchronousIo](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio), [Canceling Pending I/O Operations](https://learn.microsoft.com/en-us/windows/win32/fileio/canceling-pending-i-o-operations) | These general pages do not identify `GetBestRoute2` or `IcmpSendEcho2` as cancellable by either function. They cannot be used as evidence of a reliable IP Helper cancellation path without separate validation. |

## Consequence for the current gate

The local harness observed a 150 ms synchronous echo timeout take roughly 0.5 s, 1,000 ms calls exceed that cap by a few milliseconds, quick route lookups, and finite cleanup of nine pending IPv4 probes. Those are [machine-specific observations](go-windows-timeout-investigation.md), not Microsoft guarantees or worst-case bounds. The documented APIs alone cannot validate a conservative start margin, bounded pending drain, or bounded route phase. The user subsequently chose a v1 contract that shows `stopping` until native work and cleanup finish without promising a hard latest-return time. The start margin and route/cutoff ordering still need validation; the revised IPv4 milestone 1 timing/route gate therefore remains **unverified**, and application infrastructure remains gated.
