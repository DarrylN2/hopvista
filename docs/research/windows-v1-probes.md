## Recommended probe stack

| Measurement | Feasible route from a local Go process | Meaning and limit |
| --- | --- | --- |
| DNS | `net.Resolver.LookupNetIP` with `ip4` and `ip6` (or one `ip` lookup split by family), timed under a context. | Measures the machine's **local resolver path**, which may include cache; it is not an authoritative DNS server latency measurement. Record returned addresses and selected IP per family. [Go `net`](https://pkg.go.dev/net#Resolver.LookupNetIP) |
| Gateway and target echo | Call Windows IP Helper `IcmpCreateFile`/`IcmpSendEcho2` for IPv4 and `Icmp6CreateFile`/`Icmp6SendEcho2` for IPv6 from Go through a narrow Windows binding. | Echo RTT is the time to receive an ICMP reply, not the website's load time. The reply structs include address, status, and millisecond RTT. [IPv4 API](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2), [IPv6 API](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmp6sendecho2), [IPv4 reply](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-icmp_echo_reply), [IPv6 reply](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-icmpv6_echo_reply_lh) |
| Gateway identification | Ask Windows `GetBestRoute2` for the **selected destination IP**; read the route's `NextHop`. | The best next hop is route dependent, including VPN routes. An unspecified next hop means an on-link destination, so show `no separate gateway` rather than fabricating one. Do not infer the gateway from the first traceroute response. [GetBestRoute2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2), [route row and NextHop](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_ipforward_row2) |
| Hop trace | Reuse IP Helper echo with `IP_OPTION_INFORMATION.Ttl` set to 1, 2, ...; that field is IPv4 TTL or IPv6 Hop Limit. Read `IP_TTL_EXPIRED_TRANSIT` plus reply address for an intermediate router, `IP_SUCCESS` for arrival, and timeout for an unanswered hop. | A hop-limit-expired reply identifies the responding router interface, not necessarily every router or the forward path's physical link. Silence can mean filtering or rate limiting. Windows `tracert` documents this method and caveat. [IP options](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-ip_option_information), [IPv4 statuses](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-icmp_echo_reply), [IPv6 statuses](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-icmpv6_echo_reply_lh), [tracert](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert) |
| TCP connect | `net.Dialer.DialContext` to the selected literal IP and URL port, with `tcp4` or `tcp6`; time just the dial. | A completed TCP handshake says the port is reachable; it does not establish TLS or prove HTTP works. `DialContext`'s context ends the dial, so use later deadlines for later phases. [Go `net.Dialer`](https://pkg.go.dev/net#Dialer.DialContext) |
| TLS and HTTP | Use a fresh `net/http.Transport` with a dial function that connects to the selected IP, keeping the URL hostname for HTTP Host and TLS ServerName/certificate checks. Use `httptrace` hooks for connect, TLS handshake, and first response byte. | HTTP time to first byte (TTFB) includes server processing and transit after the request; it is not page rendering. A reused connection skips connect/TLS phases, so use a fresh transport or disable keep-alives for measured exchanges. [Go `httptrace`](https://pkg.go.dev/net/http/httptrace#ClientTrace), [Go transport](https://pkg.go.dev/net/http#Transport), [Go TLS config](https://pkg.go.dev/crypto/tls#Config), [Go client](https://pkg.go.dev/net/http#Client) |

**Permissions.** Go `golang.org/x/net/icmp.ListenPacket` documents its `ip4:icmp` and `ip6:ipv6-icmp` forms as *privileged raw ICMP endpoints*; its nonprivileged datagram ICMP forms are documented only for Darwin and Linux. Windows says `SOCK_RAW` creation requires administrator privileges. Thus raw ICMP is unsuitable for an ordinary-user Windows v1. The IP Helper echo APIs are the documented Windows route to test first; their reference pages do not state an elevation requirement. That is an evidence-based expectation, **not** a verified guarantee in this environment. Validate from a standard, unelevated Windows account before committing the interface. [Go `x/net/icmp`](https://pkg.go.dev/golang.org/x/net/icmp#ListenPacket), [Windows raw sockets](https://learn.microsoft.com/en-us/windows/win32/winsock/tcp-ip-raw-sockets-2), [IPv4 IP Helper](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2), [IPv6 IP Helper](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmp6sendecho2)

## Address families and attribution

Run IPv4 and IPv6 separately when the resolver returns usable addresses. Select **one IP per family** for the bounded run, record all returned addresses, and pin each subsequent echo, trace, TCP, TLS, and HTTP dial to that IP. A hostname can resolve to several servers or CDN edges; comparing a trace to one address with HTTP to another would tell a misleading story. Keep the original hostname in the URL, HTTP Host header, and TLS `ServerName`, so the intended virtual host and certificate are checked. For each redirect to a new hostname, resolve and pin one address of the same family, recording the new URL and IP; if that family is unavailable, report a partial redirect outcome. A custom dialer needs explicit handling of proxy policy: a proxy would change the path being measured. These are plan choices based on Go's resolver, dial, TLS, and client controls. [Go resolver](https://pkg.go.dev/net#Resolver.LookupNetIP), [Go dialer](https://pkg.go.dev/net#Dialer.DialContext), [Go TLS](https://pkg.go.dev/crypto/tls#Config), [Go HTTP client](https://pkg.go.dev/net/http#Client)

Do not equate an echo timeout with an unreachable website. ICMP can be blocked while TCP and HTTP succeed; Windows `tracert` explicitly says routers may not answer expired-TTL probes. Preserve each phase's status and error separately. A 3xx is an HTTP response, so record its TTFB and `Location` before following it. `net/http.Client` follows redirects by default and its `CheckRedirect` hook can enforce a limit; it treats non-2xx status as an HTTP response rather than a transport error. [Windows tracert](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert), [Go HTTP client](https://pkg.go.dev/net/http#Client)

## Proposed bounded run policy

These numbers are **v1 design recommendations**, not defaults promised by the underlying APIs. Keep a hard **60-second diagnostic-run deadline**; target completion around 30–45 seconds on responsive paths. Schedule independent family work concurrently, but report each family separately.

| Probe | Proposed bound |
| --- | --- |
| DNS | One lookup per hostname encountered, 2-second deadline; record resolver error and returned IPv4/IPv6 sets. |
| Gateway echo | If `GetBestRoute2` yields a separate next hop, 3 requests per family, 250 ms between starts, 900 ms per request. |
| Target echo | 5 requests per family, 300 ms between starts, 1,000 ms per request. Report received/attempted, all successful RTTs, and failures. |
| Hop trace | 1 echo per TTL, at most **16 hops** per family, 750 ms per hop; stop on destination success, a definitive unreachable status, hop 16, or the global deadline. Mark timeouts as unanswered hops and distinguish `hop limit reached` from `destination reached`. Use numeric addresses and skip reverse DNS. |
| TCP / TLS / HTTP | One measured initial HTTP exchange per family. TCP dial 2 seconds; TLS handshake 2 seconds; response headers 3 seconds; at most 3 redirects (4 HTTP exchanges total), each redirect subject to the same per-phase bounds and the global deadline. Stop on a non-redirect response, a redirect without a usable `Location`, or the redirect limit; record the final URL/host/path/status and each exchange. Cap response-body reading separately or omit it, because v1 TTFB ends at first response byte. |

The worst sequential hop-trace wait under this proposal is 12 seconds per family, much less than Windows `tracert`'s 30-hop, 4-second-per-probe defaults. Two families tracing sequentially could use 24 seconds; concurrent families use roughly 12. The global deadline still matters when the DNS, redirects, and endpoint phases time out together. A single probe per hop is deliberately a thin route sample: one unanswered hop is **unknown**, not proof of loss or an outage. Windows documents `tracert`'s `/h`, `/w`, `/d`, `/4`, and `/6` controls if a prototype uses the bundled executable as an interim fallback; output parsing and subprocess cancellation would be less reliable than structured IP Helper results. [Windows tracert](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tracert)

For RTT variation, calculate **median absolute successive RTT change** in milliseconds: for successful target-echo RTTs ordered by send time, take `|r[i] - r[i-1]|` only for adjacent successful attempts, then take the median of those differences. Require at least 3 successful replies and at least 2 valid adjacent pairs; otherwise report variation unavailable. Publish the raw RTTs and the exact formula. This is a compact, robust v1 descriptive statistic, not a standards-defined jitter measure; the endpoint may treat ICMP differently from website traffic. The receive rate is `successful echo replies / attempted echo requests`, not a network-wide packet-loss estimate.

## Feasibility checks before implementation

1. In an unelevated Windows process, call IPv4 and IPv6 IP Helper echo APIs against localhost and reachable selected addresses; verify reply layout, TTL/hop-limit option, timeout statuses, and 64-bit structure alignment. Microsoft notes 64-bit `IP_OPTION_INFORMATION32` and reply-buffer sizing requirements. [IP options](https://learn.microsoft.com/en-us/windows/win32/api/ipexport/ns-ipexport-ip_option_information), [IPv4 API](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2), [IPv6 API](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmp6sendecho2)
2. Cross-check `GetBestRoute2` for IPv4, IPv6, VPN, and on-link destinations; record chosen source, interface, and next hop. [GetBestRoute2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getbestroute2)
3. Verify that the custom HTTP dialer pins the selected IP while TLS checks the submitted hostname; inspect phase hooks on both success and error, including redirects. [Go `httptrace`](https://pkg.go.dev/net/http/httptrace#ClientTrace), [Go TLS](https://pkg.go.dev/crypto/tls#Config)

The prototype should also confirm that cancellation returns promptly while a synchronous ICMP call is waiting; the per-probe timeout bounds that wait, but a context does not cancel a synchronous Windows API call by itself. Decide whether v1 measures direct connections only or reports a proxy-specific unsupported outcome when the machine requires a proxy. [IPv4 IP Helper](https://learn.microsoft.com/en-us/windows/win32/api/icmpapi/nf-icmpapi-icmpsendecho2), [Go transport proxy controls](https://pkg.go.dev/net/http#Transport)

A lower-level component is justified only if this bounded IP Helper route cannot expose the required hop/status data or ordinary-user execution fails on supported Windows versions. Raw sockets would introduce an administrator requirement; a packet driver would add deployment and privilege complexity that the v1 measurements do not currently warrant. [Windows raw sockets](https://learn.microsoft.com/en-us/windows/win32/winsock/tcp-ip-raw-sockets-2)
