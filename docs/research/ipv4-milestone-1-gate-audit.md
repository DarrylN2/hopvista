## Required evidence still missing

1. **Validated start margin.** The provisional 250 ms allowance has unloaded and process-loaded samples; the largest observed full-cap check-to-cleanup overrun across the two loaded matrices was 26.57 ms. A real 60-second fixture passed with two CPU-bound Go workers and `GOMAXPROCS=1` during its final five seconds. These are local samples, not a worst-case bound. Define the supported Windows/account/load/network conditions and validate the candidate against them before adopting a production margin. The earlier 50 ms and 150 ms values remain diagnostic windows. The margin reduces the chance of starting too late; it is not a latest-return guarantee.
2. **Route/cutoff ordering.** The [route-phase crossing fixture](go-windows-route-cutoff.capture.json) and [loaded 60-second fixture](go-windows-minute-cutoff.capture.json) passed: after real route lookups and induced post-lookup delays crossing their cutoffs, no echo started and quiescence was recorded after phase return. This tests ordering in the harness. An actually stalled `GetBestRoute2` call remains unverified; it has no timeout/cancellation argument and may keep a run in `stopping`. A route change after lookup remains possible and must be described as a point-in-time observation.

Microsoft's [IP Helper timing and cancellation documentation review](windows-iphelper-timing-contract.md) does not provide a hard latest-return time for synchronous `IcmpSendEcho2`, a timeout or cancellation parameter for `GetBestRoute2`, or a documented way to release a pending ICMP call's buffers early by closing its handle. This limits what local repetition can establish: measured behavior on named conditions is possible, but a universal wall-clock guarantee cannot be inferred from these APIs.

## Latest first-gate check: loaded boundary matrix

The next feasible check was to extend the existing unloaded 27-call boundary matrix to all caps/paths under the minute fixture's named process-local contention condition. The new [loaded matrix](go-windows-loaded-margin-boundary.capture.json) ran unelevated on the same Windows build with two CPU-bound Go workers and `GOMAXPROCS=1`, preserving the previous capture and restoring the scheduler setting.

The diagnostic **failed its 27-started-call expectation**: one 750 ms attempt exhausted the fixture's extra 20 ms setup headroom and safely refused before native send, then closed its handle. Three deliberately short budgets also refused before handle creation. The other 26 attempts used their full caps, returned timeout 11010, and closed before their fixture deadlines. Largest observed check-to-cleanup overrun: **26.57 ms above the 1,000 ms cap**. This is larger than the prior unloaded maximum, but remains a sample, not a bound. See the [interpretation](go-windows-timeout-investigation.md#follow-up-loaded-candidate-margin-boundary-matrix). Do not count the failed matrix as passed or adopt the 250 ms candidate from these results.

Against issue #10 section 8, basic IPv4 interop, reply/error decoding, route comparison, full-cap refusal, and finite pending cleanup have existing local evidence. The remaining first-gate work concerns margin validation and whether route/native timing requires another strategy under the named conditions. The approved no-hard-drain contract removes the need to prove a universal latest-return time; it does not waive those checks. A separate standard-user account, other Windows 11 builds, system-wide load, alternate networks, and an actually stalled `GetBestRoute2` remain unverified. VPN comparison is not a first-gate requirement; IPv6 is deferred. Application slot/lifecycle/UI and packaged-executable acceptance belong to later milestones and have not been tested by this harness.

The failed run remains preserved. No existing fixture can safely manufacture a genuine stalled `GetBestRoute2`; the post-lookup delays are ordering evidence only. Keep that gap explicit rather than treating another fast route batch as a substitute.

**Follow-up completed:** the [loaded sampling check](go-windows-loaded-margin-sampling.capture.json) separately counted one safe refusal and obtained 27 actually started calls, three per cap/path. It passed its fixture checks with no deadline crossing or close failure. Its largest observed check-to-cleanup overrun was 12.64 ms; the earlier loaded 26.57 ms observation remains the larger sample. This corrects the failed matrix's sampling assumption while preserving that failure. Separate standard-user, other-build, and genuine stalled-route conditions still require environments or behavior not present here.

**Pending-drain follow-up completed:** the [loaded drain matrix](go-windows-loaded-drain-caps.capture.json) recorded nine calls pending at stop and nine returns with successful handle cleanup under the same two-worker, `GOMAXPROCS=1` condition. Stop-to-quiescent ranged from 220.94 to 952.56 ms; load progressed during every drain. The earlier unloaded 978.25 ms remains the largest observed interval. This supports the approved unbounded `stopping` contract on this machine. It does not validate the candidate margin, a production lifecycle, or an actually stalled route call.

## Assessment after loaded timing checks

The user confirmed that no separate non-admin Windows account or other Windows 11 PC is available. This does not invalidate the existing unelevated-token observations, but it leaves ordinary standard-user behavior and another-build behavior untested. Do not create an account or treat the restricted Codex sandbox identity as a substitute. The external-condition kit is ready if a suitable account or machine becomes available later.

A harness code review also found that the guarded path checked cap + margin and then sampled the clock again while computing the native timeout. A scheduling pause between those reads could have trimmed a supposedly full-cap call. The guarded experiment now derives its full timeout and refusal from one clock reading and rechecks the budget immediately before the send boundary. A unit check covers an induced post-guard pause, and the live 80 ms post-setup refusal still closes its handle without sending. This closes that specific trim path; no ordinary check can make the final clock read and Windows call entry atomic under arbitrary scheduling pauses. It adds no evidence for another account/build or a genuinely stalled route lookup.

The candidate 250 ms allowance exceeded the largest observed check-to-cleanup overrun above any cap (26.57 ms) in these captures, and no started call crossed its fixture deadline. One loaded boundary attempt and one later loaded sampling attempt safely refused after setup consumed their extra 20 ms and 50 ms sampling windows, respectively. Those windows are extra fixture budget beyond cap + 250 ms, not alternative proposed margins. The second guard behaved as intended. The loaded drain matrix adds finite resource-ownership evidence during cancellation. These observations support continuing to investigate the candidate on this build and load condition; they do not validate a conservative production margin across Windows 11 x64.

Only one Windows 11 build, one unelevated token (not a separate standard-user account), one current IPv4 network, and process-local load are represented. The test does not bound scheduler pauses between the final guard and native entry or a synchronous `GetBestRoute2` already in progress. Issue #10 allows `stopping` until native work completes and makes no hard latest-return promise, so a mathematical worst-case drain bound is not required. Still, no actual delayed route call has demonstrated its cleanup path, and these samples cannot be promoted into an all-Windows-11 margin claim. **Gate decision: open; 250 ms remains provisional.** Application infrastructure remains gated.

## Approved timing contract

The 60-second cutoff stops new measurement work. An already-started route lookup or native echo may finish afterward. Keep the one-run slot occupied and show `stopping` until all native work and cleanup finish; do not promise a hard latest terminal time. Recheck the remaining full-cap budget after route selection and immediately before native send. Issue #10 now records this choice. The numerical 50 ms and 150 ms investigation allowances remain unapproved production margins.

The combined local evidence has been assessed above and remains insufficient to adopt a production margin for Windows 11 x64. The user has neither a separate non-admin account nor another Windows 11 PC. The prepared [external-condition recheck](ipv4-external-condition-recheck.md) is ready if a suitable environment becomes available later; its step statuses require raw-outcome review. An actually stalled `GetBestRoute2` remains unverified; simulated post-lookup pauses do not substitute. Keep the 250 ms margin provisional and the gate open; do not infer a hard native return bound from finite captures.

The [external-condition recheck](ipv4-external-condition-recheck.md) now packages the existing harness checks and records a local manifest plus fresh captures on another ordinary Windows session. The current personal accounts are administrators (the tested process used a filtered token), and the Codex sandbox accounts cannot furnish ordinary-user native evidence. This machine cannot supply a second Windows 11 build. The recheck kit is preparation for those real executions, not their result. No new account, Windows configuration change, or application code was made.

If those checks fail, keep the gate open and revisit the design. The current asynchronous experiment submitted and completed calls but did not establish a safe pending-operation cancellation bound. Do not infer a feasibility pass from finite local samples, the IPv4-only scope choice, or the no-hard-drain decision.

There is no further local test presently identified that can demonstrate the missing account/build conditions or force a genuine `GetBestRoute2` stall without changing the test environment. Repeating quick route calls, unloaded timing samples, or post-lookup sleeps would only add samples of already-tested behavior. The first gate therefore remains **open** under the agreed Windows 11 x64 scope, and application code must wait for new evidence or an explicit scope/acceptance change. This is an evidence limit, not a failed IPv4 interop result.
