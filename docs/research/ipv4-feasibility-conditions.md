**Current status, 2026-10-14:** the user approved an empirical development gate on this machine, and [final verification passed](ipv4-development-gate-final-review.md). The 250 ms initial policy is approved for development; release acceptance and broad Windows/account coverage remain unverified. Earlier open-gate/provisional-margin statements below are historical, superseded by the explicit revision rather than new evidence for another account/build or a genuine native route stall.

Reviewed 2026-10-14 against [issue #10](https://github.com/DarrylN2/hopvista/issues/10) and the [milestone 1 gate audit](ipv4-milestone-1-gate-audit.md). The user chose **Windows 11 64-bit for the IPv4-only first release**. The concrete first executable target is x64 (`windows/amd64`), matching the harness architecture; Windows on ARM64 needs separate validation before support is claimed. Windows 10 is outside the first-release scope. This inventory distinguishes the chosen scope from the first Go Windows feasibility evidence; the scope choice is not a gate pass.

## Boundary between the first gate and release support

The later [loaded boundary matrix](go-windows-loaded-margin-boundary.capture.json) extended process-local contention to all three caps and paths. It **failed its expectation of 27 started calls**: one attempt safely refused after setup used the extra 20 ms budget; 26 full-cap calls completed and closed before their fixture deadlines. The largest observed check-to-cleanup overrun was 26.57 ms above the 1,000 ms cap. Both workers started before sampling, progress was recorded around every attempted full-cap call, and `GOMAXPROCS` was restored. This adds one measured condition; it does not validate the candidate or any of the missing account/build/network/stalled-route conditions. Pending cancellation under load remains untested.

The [follow-up loaded sampling](go-windows-loaded-margin-sampling.capture.json) allowed safe setup refusals and collected three actual full-cap calls for every cap/path: 27 completed calls and one safe refusal in 28 attempts. The largest overrun in that run was 12.64 ms; the earlier 26.57 ms observation remains. The new fixture passed its sampling checks on the same build and unelevated token, while the 250 ms margin and gate remain unapproved.

The [loaded pending-drain matrix](go-windows-loaded-drain-caps.capture.json) then recorded nine calls pending at stop across the three caps and paths. All returned and closed successfully with worker progress during drain; the largest stop-to-quiescent interval was 952.56 ms. This adds finite cleanup observations under the same process-local contention. It does not supply a maximum return time or validate other account, build, network, or genuinely delayed route conditions.

Issue #10 requires a small actual-Go IPv4 Windows harness before application infrastructure. It also requires a conservative start margin and honest stop/cleanup ordering on **tested Windows conditions**. The captures establish behavior on the named machine and paths above. The first-release platform target is now Windows 11 x64, but one build and one account token do not establish coverage across that whole target. Release acceptance later requires live checks of the packaged executable and its production adapter; this harness cannot supply that evidence.

An active VPN comparison and remote IPv6 are not first-gate substitutes: VPN remains untested, and IPv6 is deferred beyond the IPv4-only first release. A separate standard-user account, another Windows 11 build, system-wide load, and a truly delayed `GetBestRoute2` have not been exercised. Those absences must remain visible whenever the evidence is used; they cannot be counted as passing checks. Windows 10 and ARM64 need their own future support decision and validation.

The remaining feasibility question is whether the 250 ms candidate margin and route/cutoff behavior have enough evidence for the **Windows 11 x64** first gate, with unsupported conditions stated plainly. The margin is still a local candidate and the milestone 1 feasibility gate remains **open**. The chosen platform scope does not validate the margin or authorize application infrastructure.

The user has confirmed that this is the only available Windows 11 PC and that no separate non-admin account is available. The tested-condition inventory therefore cannot be expanded to another build or ordinary standard-user account now. The existing unelevated-token evidence remains valid for this machine; the unavailable conditions stay unverified. The prepared [external-condition recheck](ipv4-external-condition-recheck.md) can be used if access changes later.
