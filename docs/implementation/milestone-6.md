# Milestone 6: production IPv4 route/echo adapter and path sampling

`internal/probe/windowsipv4` now implements the normalized synchronous adapter with `GetBestRoute2` and `IcmpSendEcho2`. It uses the reviewed standalone harness's Windows x64 layouts and reply classifications. An unspecified route next hop is recorded as on-link, with no separate gateway. Each echo keeps its native handle until send and close finish, checks the full cap plus the empirically accepted 250 ms margin before setup, after setup, and immediately before send, and never trims the configured native timeout to fit remaining time. Route lookup remains synchronous with no claimed native time bound or cancellation mechanism. A context cancellation stops new work, not a native call already in progress.

`internal/pathmeasure` runs the issue #10 IPv4 plan through `probe.Adapter`: route-specific gateway selection, three 900 ms gateway echoes with 250 ms start spacing when a separate gateway exists, five 1,000 ms target echoes with 300 ms start spacing, and one 750 ms echo per TTL through the configured maximum of 16. It continues after silent hops and stops the trace on a destination reply, unreachable reply, hop limit, cancellation, or deadline. It records raw replies and unavailable RTT variation when evidence is insufficient; available variation is the median absolute change between adjacent successful target samples in send order. A route returning after cutoff does not schedule any echo. The caller supplies whether the path is for a final or attempted host.

Deterministic fake-adapter tests cover on-link and separate-gateway plans, target sample counts and variation, a silent intermediate hop followed by a destination reply, unreachable termination, and route return after the cutoff. Windows adapter tests check ABI layout, status normalization, and pre-start refusals. On 2026-10-14 an opt-in unelevated production-adapter loopback test passed outside the socket-restricted sandbox: `HOPVISTA_LIVE_ADAPTER=1 go test ./internal/probe/windowsipv4 -run TestLiveLoopback -count=1 -v`. It checked a live on-link route and echo reply. This is limited local production-adapter evidence, not packaged-executable or release acceptance.

The preview app still uses `measurement_not_connected`. The next slice connects DNS, pinned HTTP, and path sampling through the run lifecycle and local API. Release acceptance remains open. The 250 ms margin remains empirical; a genuinely stalled native `GetBestRoute2` call, another Windows account, broader Windows 11 builds and network conditions, and packaged-executable behavior remain unverified.
