# Milestone 18: packaged pinned HTTPS compared with curl

On 2026-10-15, an opt-in isolated executable check measured `https://example.com/` through HopVista's direct pinned IPv4 transport on the current Windows 11 x64 machine. Its one HTTP exchange recorded the selected IPv4 address as the actual connected peer, completed TCP, TLS, and first-response-header-byte phases, an HTTP response, and no connection reuse. The successful TLS phase used ordinary certificate verification for the URL hostname. A separate system `curl.exe` request used `--resolve` to pin that same hostname, port, and IPv4 address and `--noproxy '*'` to bypass proxies. Curl's connected peer and HTTP status matched the packaged app, certificate verification succeeded, and the first-byte timings fell within the test's broad two-second comparison range. Exact milliseconds are not expected to match across separate requests.

Set `HOPVISTA_PACKAGED_HTTPS_URL=https://example.com/` alongside `HOPVISTA_PACKAGED_EXE` and run the opt-in command in [the smoke-check README](../../tools/app-smoke/README.md) where direct public HTTPS is permitted. The isolated executable check passed outside the network-restricted command sandbox. The root Go suite and `go vet ./...` were run after this change.

This checks one public hostname, one selected address, and one current network condition. The controlled TLS fixtures still provide the wrong-name, untrusted-certificate, IP-literal, and SNI rejection/acceptance cases. This live comparison does not validate every public site, proxy/browser equivalence, another Windows account/build/network, or a genuinely stalled `GetBestRoute2`. The 250 ms native start margin remains empirical; release acceptance remains open.
